# InsightKartta Project Context

This file exists to give a future LLM/chatbot enough context to continue the project effectively without re-deriving decisions from scratch.

Use this file as project memory.

---

## 1. Project identity

Project name:
- InsightKartta

Purpose:
- a portfolio-quality software engineering project
- analyzes Finnish statistics from Statistics Finland
- intended to demonstrate architecture, data engineering, backend, frontend, and interactive visualization skills
- not intended to be just a plotting exercise

Main design philosophy:
- config-driven
- extensible
- normalize datasets into a shared frontend-friendly shape
- preserve a clear project structure and explicit decisions

## 2. Current high-level architecture

Two parallel data pipelines feed into a single API and frontend:

### StatFin pipeline (config-driven)
1. datasets are declared in `backend/pipelines/config/datasets.yaml`
2. ingestion fetches raw StatFin data into `backend/data/raw/<dataset>/`
3. transformation reads the latest raw file, applies generic config-driven steps, and writes `backend/data/processed/<dataset>/latest.csv`
4. `run_analysis.py` reads each dataset, runs `GenericAnalysis`, and writes `backend/data/analysis/<dataset>.json`

### Elections pipeline (custom)
1. `fetch_municipal_elections.py` scrapes HTML from vaalit.fi into `backend/data/raw/municipal_elections_party_votes/<year>/`
2. `normalize_party_votes.py` parses the HTML into `backend/data/processed/municipal_elections_party_votes/latest.csv`
3. `generate_region_insights.py` produces two outputs:
   - `backend/data/analysis/region_insights/<region_code>.json` — per-municipality insight JSON with party changes, raw indicator changes (`indicators`), and indicator-vs-national context (`indicator_relationships`)
   - `backend/data/analysis/election_indicator_correlations.json` — national-level Pearson correlations between indicator changes and party vote share changes across all municipalities

### Shared output
5. FastAPI serves datasets generically
6. React frontend renders chart + map + insights using normalized data and metadata

## 4. Core backend decisions already made

### 4.1 Config-driven datasets
A StatFin dataset should be addable mainly by editing `backend/pipelines/config/datasets.yaml`.

The elections dataset is an explicit exception — it uses a fully custom pipeline.

### 4.2 Generic analysis for all datasets
`GenericAnalysis` in `backend/pipelines/analysis/generic.py` runs for every dataset declared in `datasets.yaml`. It:
- filters to the national aggregate row (`region_code == "SSS"`)
- computes trend, average, and peak year on the `value` column
- uses `metadata.label` from the dataset config for human-readable insight text

`run_analysis.py` now saves results to `backend/data/analysis/<dataset>.json`. The API reads these files. There is no longer a need to add a dataset-specific analysis class for standard datasets.

`UnemploymentAnalysis` (`backend/pipelines/analysis/unemployment/analysis.py`) still exists but is no longer wired into the pipeline. It is now surplus and could be deleted if the dataset never needs genuinely custom analysis logic.

### 4.3 Unified frontend contract
The frontend works against a normalized row shape:

```json
{
  "region_code": "KU091",
  "region_name": "Helsinki",
  "year": 2024,
  "value": 12.3
}
```

`region_code` is the canonical column name across all processed CSVs, including elections. Use `region_name` in the frontend (for display and map matching); `region_code` is available but rarely needed.

### 4.7 Region insight JSON shape

Each `backend/data/analysis/region_insights/<region_code>.json` file contains:

```json
{
  "region": { "code": "KU091", "name": "Helsinki" },
  "election_summary": { "latest_year": 2025, "previous_year": 2021 },
  "party_changes": [ ... ],
  "indicators": {
    "unemployment": {
      "election_start_year": 2021, "election_end_year": 2025,
      "indicator_start_year": 2021, "indicator_end_year": 2024,
      "start_value": 11.0, "end_value": 12.3,
      "absolute_change": 1.3, "relative_change_pct": 11.8
    }
  },
  "indicator_relationships": {
    "unemployment": {
      "election_period": { "start": 2021, "end": 2025 },
      "regional_absolute_change": 1.3,
      "national_absolute_change": 1.5,
      "deviation_from_national": -0.2,
      "relative_to_national": "similar",
      "data_status": "complete"
    }
  }
}
```

`indicators` contains the raw change data from `indicator_change_calculator.py`. `indicator_relationships` adds national context from `relationship_calculator.py`. Both sections are needed — do not remove either.

The `national_absolute_change` in `indicator_relationships` is the **mean of KU... municipality changes**, not the SSS national total. The SSS row for population is Finland's total population change (~104k), which makes every municipality look "below average". Mean-of-municipalities is the correct reference for per-municipality comparison across all indicator types.

### 4.8 National correlations file

`backend/data/analysis/election_indicator_correlations.json` is produced by `generate_region_insights.py` and served by `GET /elections/correlations`. It contains Pearson r between each indicator's change and each major party's vote share change across all municipalities, keyed by election year. Returns 404 from the API if the file has not been generated yet.

### 4.4 CSV for processed data
Processed storage is CSV. FastAPI and analysis code load from `backend/data/processed/<dataset>/latest.csv`. Do not assume parquet.

### 4.5 Metadata is required
Datasets need metadata for the frontend:
- `label`
- `unit`
- `visualization.map.bins` — 5 values required; the colour scale uses all five thresholds

Without this, the frontend becomes brittle or visually misleading.

### 4.6 Config is cached at startup
`load_config()` in `dataset_service.py` is decorated with `@lru_cache(maxsize=1)`. The YAML is read once per process. Restart the server after changing `datasets.yaml`.

## 5. Current frontend decisions already made

### 5.1 Frontend should be generic
Avoid dataset-specific frontend logic like:
- hardcoded metric names
- hardcoded dataset names
- hardcoded `/unemployment` assumptions

Instead:
- dataset list comes from `/datasets`
- selected dataset comes from `/{dataset_name}`
- chart uses `value`
- title and units come from `meta`

### 5.2 Use `region_name` in the frontend
The UI uses `region_name` rather than `region_code` because the GeoJSON is name-based. Chart selection and map matching both use `region_name`.

### 5.3 Map bins must be dataset-aware
The frontend reads `meta.visualization.map.bins` for the colour scale. The colour function (`getColor` in `mapScale.js`) uses 5 thresholds to produce 6 colour bands. Bins must have exactly 5 values for all bands to render correctly.

### 5.4 Single canonical colour function
`getColor(value, bins)` from `frontend/src/utils/mapScale.js` is the only colour utility. Both `MapView` and `MapLegend` import from this file. There is no `colorScale.js` — it was deleted. Do not add a second implementation.

### 5.5 GeoJSON lifecycle gotchas already encountered
React Leaflet `onEachFeature` does not automatically refresh when state changes.

Known fixes:
- use a changing `key` on the `GeoJSON` component (already implemented, keyed by `year`)
- do not mount the layer before data is ready

### 5.6 Unit string format
Unit strings in `datasets.yaml` should not have a leading space. The frontend adds its own separator. Example: `unit: "%"` not `unit: " %"`.

## 6. Current dataset registry expectations

Every StatFin dataset entry in `backend/pipelines/config/datasets.yaml` must include:

- `name`
- `source`
- `endpoint`
- `payload`
- `transformation`
- `metadata`

Typical transformation block:

```yaml
transformation:
  dimensions:
    region: Alue
    year: Vuosi

  rename:
    some_source_metric: cleaned_metric_name

  types:
    year: int

  value_column: cleaned_metric_name

  filters: []

  join:
    region_mapping: true
```

Typical metadata block:

```yaml
metadata:
  label: "Human-readable label"
  unit: "%"
  visualization:
    map:
      bins: [10, 20, 30, 40, 50]
```

`bins` must have exactly 5 values.

## 7. YAML anchors decision

Do **not** add extra config loader complexity for reusing area-code lists.

Use YAML anchors and aliases directly in `datasets.yaml`. PyYAML resolves them automatically. This is an explicit decision and should be respected.

## 8. Datasets already worked on

### 8.1 Unemployment
The original dataset. Analysis runs via `GenericAnalysis`. `UnemploymentAnalysis` still exists on disk but is no longer called.

### 8.2 Education
Two datasets: `education_upper_secondary` and `education_tertiary`. Both fully operational. Analysis runs via `GenericAnalysis`.

Lesson from implementation: PXWeb payloads for education required explicit `Tiedot` selection; empty query returns unexpected dimensions.

### 8.3 Population
Fully operational. Analysis runs via `GenericAnalysis`. Unit is `"persons"` (no leading space).

### 8.4 Municipal elections
Fully operational but uses a custom pipeline entirely outside `datasets.yaml`. Scripts run in this order:
1. `fetch_municipal_elections.py` — scrapes HTML
2. `normalize_party_votes.py` — parses HTML into processed CSV with `region_code` column
3. `generate_region_insights.py` — produces two outputs:
   - 292 per-municipality JSONs in `backend/data/analysis/region_insights/`
   - `backend/data/analysis/election_indicator_correlations.json`

`generate_region_insights.py` derives its indicator dataset list from `datasets.yaml` (not hardcoded), so new StatFin datasets are automatically included as indicators and in the correlation analysis.

`relationship_calculator.py` in `backend/services/` contains the core logic for both new outputs. It uses the mean of KU... municipality changes as the national baseline (not the SSS row) to ensure the comparison is meaningful for all indicator types including population.

## 9. Geography and mapping decisions

Known facts:
- StatFin area values may include `SSS`, `KU...`, `MK...`, and other aggregates
- GeoJSON files may be municipality-level or region-level
- names in GeoJSON must match `region_name` exactly for map coloring and tooltips to work
- the frontend map currently hardcodes `kunnat.geojson` and reads `feature.properties.Kunta` — it assumes municipality-level data

`region_code` is the canonical code column in all processed CSVs.

## 10. Common mistakes already made

### 10.1 Forgetting metadata
Adding a dataset without `label`, `unit`, and `visualization.map.bins` breaks the frontend visually.

### 10.2 Forgetting `value_column`
If `value_column` is missing or wrong, transformation fails.

### 10.3 Hardcoding dataset-specific logic in the frontend
Examples of outdated patterns that were removed:
- `analysis.UnemploymentAnalysis`
- `dataKey="unemployment_rate"`
- hardcoded `/unemployment` route assumptions

### 10.4 Assuming the frontend should use region codes
The frontend uses `region_name` for display and map matching. `region_code` exists in the data but is not needed by the frontend for normal rendering.

### 10.5 Overcomplicating config loading
A custom reference resolver for selections was proposed and then rejected in favour of YAML anchors.

### 10.6 Dataset-specific analysis for trivial cases
`UnemploymentAnalysis` used to be the only analysis module. It was effectively the same as what `GenericAnalysis` now does. Use `GenericAnalysis` by default; only add a dataset-specific module if the logic is genuinely different.

### 10.7 Units with a leading space
`unit: " persons"` produced double-spaced output. Unit strings should not start with a space.

### 10.8 Parallel colour implementations
Having both `colorScale.js` (hardcoded) and `mapScale.js` (bin-driven) caused the legend and map to use different colour functions. The fix was to delete `colorScale.js` and use `mapScale.js` everywhere. Do not add a second colour utility.

### 10.9 Using the SSS row as the "national average" for absolute-count indicators
The SSS row is a national aggregate total, not a per-municipality average. For population, SSS represents ~104k persons added to Finland — making every single municipality look "below national average". The correct reference for per-municipality comparison is the mean of KU... municipality changes, computed in `compute_indicator_baselines()`.

### 10.10 Using `vote_change` instead of `vote_share_change_pct`
`vote_change` is a raw vote count delta. It is not comparable across municipalities — a 500-vote gain in Akaa is not equivalent to a 500-vote gain in Helsinki. Always use `vote_share_change_pct` (percentage points) for cross-municipality election comparisons.

### 10.11 Opening region insight links in a new tab
Using `target="_blank"` on the Leaflet popup link causes the region page to open in a new tab. Clicking "Back to map" then puts the user back at `/` in that new tab, resulting in two main-view tabs. The popup should use a plain `<a href>` without `target="_blank"`, and the back link in `RegionPage` should use React Router `<Link to="/">`.

### 10.12 Forgetting that `generate_region_insights.py` produces two outputs
The script writes both per-region JSONs and `election_indicator_correlations.json`. If you change `relationship_calculator.py`, you must re-run `make region-insights` to regenerate both. The API endpoint `GET /elections/correlations` returns 404 until the file exists.

## 11. Important implementation preferences

When continuing this project:

- prefer config changes over new one-off code
- prefer generic pipeline steps over custom dataset modules
- prefer metadata-driven frontend behavior
- prefer explicit documented decisions over silent assumptions
- preserve the architecture rather than bypass it for speed
- the elections pipeline is a known explicit exception to the config-driven pattern — treat it as such, not as a model to replicate for future datasets

## 13. Summary for a future assistant

InsightKartta is a config-driven multi-dataset analytics platform. Most of the pipeline is generic: add a dataset to `datasets.yaml` and it automatically gets ingestion, transformation, analysis, and API exposure.

The elections dataset is a deliberately different case. It requires HTML scraping and party-level parsing that doesn't fit the generic PXWeb pipeline. This is an explicit architectural exception, not a model to follow.

If a future suggestion:
- adds hardcoded dataset-specific logic where config would suffice
- ignores metadata requirements
- ignores geography alignment
- reintroduces old parquet-specific paths
- adds a second colour scale utility alongside `mapScale.js`
- adds a dataset-specific analysis class for something `GenericAnalysis` can already handle

then that suggestion is probably going in the wrong direction.
